# تأییدها و Sentinel

## این چیست؟
Sentinel دروازهٔ امنیتی OpenMuse است. **هر** فراخوانی ابزار ایجنت اول از آن رد می‌شود و یکی از سه جواب را می‌گیرد: `allow` (اجرا)، `ask` (اول از من بپرس) یا `deny` (هرگز). همین قول اصلی زول را نگه می‌دارد: «قبل از هر کار برگشت‌ناپذیر تأیید بگیر».

## چه کار می‌کند؟
- **حالت `ask`:** کارهای بی‌خطر و متوسط آزادند. کارهای حساس (برگشت‌ناپذیر یا بیرونی) کارت تأیید می‌سازند.
- **همیشه با تأیید**، هر سطح خطری که داشته باشند: `send_email`، `shell`، `python_execute`، `browser` و `forget` (پاک کردن حافظه).
- **ردیابی آلودگی (taint):** بعد از اینکه ایجنت دادهٔ خصوصی خواند (مثلاً ایمیل)، فرستادن درخواست به دامنه‌ای خارج از فهرست مجاز هم تأیید می‌خواهد. این جلوی نشت داده با prompt injection را می‌گیرد.
- اگر به کارت تأیید تا یک ساعت جواب داده نشود، «رد» حساب می‌شود.
- هر تصمیم در `/data/openmuse/audit.jsonl` ثبت می‌شود.
- تأییدها را می‌شود محدود کرد، مثلاً «ایمیل فقط به این آدرس».
- **ایزوله‌سازی:** هر دستور shell یا Python در صورت امکان داخل bubblewrap اجرا می‌شود (`sandbox.mode = "auto"`).

## کجای کد است؟
| فایل | نقش |
|---|---|
| `engine/openmuse/config.toml` (بخش‌های `[sentinel]` و `[sandbox]`) | سیاست تأیید زول |
| `Dockerfile` | نصب `bubblewrap` |

## تنظیمات
فقط در `config.toml`. **شل کردن این قوانین (کم کردن از `always_ask_tools` یا تغییر `mode` به `auto`) فقط با تصمیم صریح حسین است** ([RULES.md](../RULES.md)).

## تست
- دستی: از ایجنت بخواه یک دستور shell اجرا کند. باید کارت تأیید بیاید.
- لاگ شروع موتور می‌گوید جعبه فعال است یا نه. اگر `commands run unboxed` دیدی یعنی bubblewrap کار نمی‌کند.

## نکته‌ها و محدودیت‌ها
- bubblewrap فقط روی لینوکس و فقط وقتی هسته اجازهٔ user namespace بدهد کار می‌کند. **روی همروش کار نمی‌کند** (لاگ: `bwrap: No permissions to create a new namespace`). پس دستوری که تأیید کنی به کل کانتینر دسترسی دارد، از جمله `/data` و متغیرهای محیطی. قبل از تأیید shell، دستور را با دقت بخوان.
- Sentinel متن پیام‌ها را «دستور» حساب نمی‌کند. ایمیل یا پیامی که ایجنت می‌خواند داده است و نمی‌تواند تأیید بدهد.
